# Admission and complete thread lifetime

The admission contract is defined in `closure/traffic-refinement/admission-spec.json`. Its candidate proofs and runtime witnesses become evidence only when the root closure gate freezes their input hashes and reports a result. This document does not independently declare closure.

A successful listener constructs its own normalized immutable traffic profile, `Admission`, credit bucket, owner set, lock and empty request-thread registry. `Admission.reserve` and `release` serialize on the admission lock. Successful reservation owns the actual accepted socket before allocating a Python request thread. Rejected capacity or credit requests receive a bounded constant refusal attempt and close without creating a request thread or request parser.

Reservations survive complete thread termination. The v5 reaper first skips any already-uncertain owner and any current-thread entry. For another registered owner it adds an uncertainty mark before calling `join(timeout=0)` and `is_alive()` inside one observation transaction. `RuntimeError` continues with the mark retained; every other exception propagates with the same mark retained. Future passes never query an uncertain owner again. Only normal return from both observations clears the mark. A live result retains the reservation; a dead result then removes the registry entry and releases exactly that owner. Clearing the mark precedes removal, so uncertain owners remain a subset of registered owners. No helper thread is created.

The previous handler-finally release was insufficient for a strict live-thread bound. `build/trf-closure/trf01-thread-teardown-discovery/result.json` records the deterministic counterexample: two live request threads with a one-handler limit, after each was paused immediately following reservation release. The original source, witness and v1 candidate specification are preserved there. The thread-tail regression pauses a real request thread after the handler callback returns; the repaired server retains its reservation and refuses the next allocation until that thread exits.

A second deterministic counterexample in `build/trf-closure/trf01-delayed-bootstrap-discovery` interrupted `Thread.start` after native launch but before bootstrap published `ident`. Releasing on `ident is None and not is_alive()` allowed two live request threads under a one-handler cap. The v3 repair recorded attempted start and retained unpublished owners. A third constructed counterexample in `build/trf-closure/ting02-ident-publication` exposed another native bootstrap interval: `ident` was already published, `_started` was not set, and inherited `is_alive()` returned false while the native thread was alive. That old reaper again admitted two live request threads under a one-handler cap. The v4 repair requires a zero-time join to return before using the liveness observation. The same native witness records two live threads before the repair and one afterward. If bootstrap never becomes joinable, its bounded slot remains visible in `activeHandlers`; restarting the service recovers that capacity. Reclaim liveness after this exceptional ambiguity is outside TRF-01.

A fourth local counterexample, `build/trf-closure/ting02-observation-interruption/before.json`, raises `RuntimeError` once from the actual CPython thread status-lock acquisition. The installed helper releases the still-owned status lock and marks the thread stopped before rethrowing. The first old reaper pass retains the slot, but its second pass trusts the poisoned metadata and releases it while the handler barrier remains held; the next reservation produces two live handlers under a one-handler cap. This is a local deterministic concurrency witness, not a deployed-system test. The v5 policy is frozen before its implementation and retains failed observations permanently instead of relying on a later apparently successful join.

The formal boundary includes exceptions from both observation primitives. It separately models lock-serialized set/dict/count bookkeeping as atomic CPython operations; it does not claim safety against asynchronous cancellation at every arbitrary bookkeeping bytecode. Reliability must follow the reachable history from empty state: successful observation starts only from a reliable owner; failed observation transitions to sticky uncertainty and never returns to reliability. Unknown owners remain reserved and registered, so the uncertain set and potentially live thread count stay within the existing cap. A normal self-observation skips before marking and therefore causes no capacity loss. Exceptional quarantined capacity is recovered by process restart, not by retries against the same Thread metadata.

The independent Lean evaluator has no hidden capacity repair. Its actual guard and count deltas are emitted from the Python AST. A `>=` to `>` mutation lowers to an executable permissive guard and fails the independent theorem. Increment, decrement and reversed-lane mutations also lower and fail the proof. Unsupported syntax, removed locks/guards, owner changes, reordering allocation before registration, lost cleanup and control-topology changes fail closed in the source adapter. The complete AST of every registered critical method and constructor is covered, not just selected anchors. Module envelopes close relevant imports, decorators, bases and top-level bindings.

Ownership is represented by an injectively named list of socket/object identities; list order has no observable significance for the production set. Custom constructive list proofs establish distinctness, exact owner count, idempotent exact-owner release and preservation of other owners. Every lock-linearized reserve/release trace starting with empty ownership stays within the selected lane bound. Anonymous reservations allocate a fresh Python identity and release the last anonymous identity; the adapter checks both branches. Arbitrary external mutation, subclass overrides and monkey-patching are outside the certified production execution boundary.

The thread proof uses an augmented per-owner ledger: a successful reservation initially has a reserved-before-thread entry, then progresses through allocated, attempted-start, identity-published-but-not-started, running and dead phases. The concrete registry covers allocated, attempted, identified, running and dead entries. Native liveness and Python `is_alive` are separate observations: identified threads can be natively alive while `is_alive` is false. Zero-time join refuses that phase. For a reliable observation history, the extracted joined reaping predicate accepts only dead phases; Lean constructs the identity-only counterexample and proves that join refusal and identified-phase reaping preserve ownership. Reserve, phase change, failed-before-attempt cleanup and dead-only reaping preserve the identity relation inductively from an empty initial state. Thus the ledger cardinality, concrete registry cardinality and live request threads are all bounded by the lane reservation cap. The intermediate reserved-before-thread phase matters: equality between the concrete registry and owners need not hold while a reserved socket is waiting to enter the allocation lock. The proof does not assume this false equality.

`main` constructs one public listener. Its default `--control-port=0` creates no control listener and carries no private-health availability claim. With a nonzero distinct control port and successful constructors, `main` creates exactly one additional listener bound to literal `127.0.0.1`; both constructors use equal default normalized profile values. Each has separate locks, owners and credit buckets. The enabled default envelope is 30 public plus 2 control handlers, 60 plus 4 burst credits and 30 plus 2 credits per second. No lane can borrow another lane's owner or credit state. Paired real-socket tests fill the public listener while exercising the enabled control health route, then fill both lanes and witness the combined cap.

Credit refill is lowered from the production `min(capacity, credit + elapsed * rate)` arithmetic, with elapsed denoting the nonnegative clamped clock difference. Lean proves remaining credit at most capacity, exact successful subtraction without negative credit, and the arithmetic sum of independent lane bounds. The full admissions-over-time/refill interval claim remains TRF-02. It is not inferred from handler capacity or from tests.

Socket acceptance precedes reservation. Under the declared standard-library contract of one serialized `accept`/`process_request` callback per serving listener, at most one accepted-but-unreserved socket exists per listener, at most two for the enabled pair. Those pending sockets are additional to reserved handlers and the separately configured public/control kernel backlogs. The OS may implement `listen(backlog)` differently; a whole-process socket/RSS accounting theorem and deployment/proxy guarantees remain separate TRF-03/TRF-21 obligations. The lifecycle representation's single pending slot relies on that explicit stdlib serialization primitive, not an assumption that accept happens after reserve.

Proof trust includes the pinned Lean kernel; Python exact integers, identity, set/list operations and lock semantics; the closed AST adapter and stated ownership-erasing projection; standard-library `Thread.start`/bootstrap, normal observations with an uninterrupted reliable history, request cleanup and listener serialization; failures of `join` or `is_alive` are explicitly permitted to invalidate metadata and trigger permanent uncertainty; and OS socket/loopback behavior. Complete credit/peer work is erased only because its closed source writes buckets, peers, local values and diagnostic counters without writing ownership/count state. This primitive interpretation is declared trust, not an axiom inserted into Lean. All project definitions and theorems have empty transitive axiom sets, including no `propext`, `Classical.choice`, `Quot.sound` or placeholder proofs.

Focused checks are `python -m unittest discover -s tests -p test_ingress_admission.py` and the corresponding `test_admission_bridge.py` command. Lean modules compile in order `AdmissionModel`, `AdmissionExtracted`, `AdmissionSpec` through `scripts/lean_offline.py`, with `-DgenInjectivity=false`; the final closure gate runs and inventories them in two clean offline builds.

# v0.0.5-alpha

This prerelease improves timeout handling and reduces default concurrency for a
two-to-four-core host. It preserves every existing portal feature and both hint
metrics, with Canonical still the default.

- The constrained profile uses one feedback and one behavior JVM, one advertised
  processor per JVM, and separate startup/analysis allowances. Standard and
  explicit worker settings remain available, including one-shot rollback mode.
- Queued work expires without waiting for a preceding job to finish. Capacity
  waits before launch no longer poison the startup-failure circuit. Cleanup
  retains uncertain process ownership until termination is confirmed.
- Feedback cooperatively returns `WORK_LIMIT` before its hard worker deadline
  when charged work expires. It publishes no partial winner and reuses the JVM
  on the next request. Parsing, native solver calls and OS scheduling remain
  outside that cooperative guarantee.
- Local and IIS launchers carry the same resource settings. ARR uses a minimum
  120-second timeout, the browser 150 seconds; timestamped private IIS packages
  include the new runtime module. Installed task settings are preserved until
  explicitly updated.
- AP01 work/fuel limits, launch budgets, private diagnostics, strict editing
  identity and fallback handling, default-denied administrator networks, and
  source-freshness reporting are included. Existing supporting evidence stays
  in the repository.

The [constrained-runtime report](../constrained-runtime-implementation.md) records
**1,448 identical complete responses** against the preserved AP01 baseline: all
181 exercises, starter/correct bodies, both metrics, at two and four logical
CPUs. Each scenario shared 12 identical concurrent checks as one computation,
served 12 cached checks without computation, and handled eight subsequent edits
without launching another JVM. Forced 20 ms cooperative limits returned in
27–29 ms and recovered in the same PID. Affinity is not a VPS quota or an
old-processor simulation; these measurements do not claim a universal speedup.

The [local application record](../../closure/constrained-runtime/evidence/validation-20261005T102953Z-842f4bea/report.json)
passed 1,228 Python tests, 378 engine checks, 86 public browser checks, 14
administrator browser checks, seven dashboard checks and 69 HTTP comparisons.
The proof-runner repair has additional separate checks and does not change the
application inputs tested by that record.

[Native IIS acceptance](https://github.com/AnonymousAlloyLab/AlloyStudio/actions/runs/37300331432)
passed all **138 recorded checks** on Windows Server 2022 with IIS/ARR and a real
LOCAL SERVICE backend. The [retained evidence](../../closure/constrained-runtime/evidence/native-iis-run-37300331432/README.md)
covers both hint metrics, behavioral instances, JVM reuse, administration network
rules, restart/stop cleanup and an unaffected second IIS site. Three earlier
failures are preserved with their fixes. This validates the disposable loopback
deployment; production TLS/Cloudflare, reboot and live provider calls are outside
its scope.

The new [LP05 Java/Lean slice](../../formal/work_budget/README.md) covers parsed
charge/checkpoint transitions and signed integer arithmetic. It uses audited
Lean foundational axioms, introduces no project axioms or placeholder proofs,
and does not close whole-production refinement or absolute wall-clock bounds.
Historical closures remain bound to their historical input roots.
The [restricted LP05 report](../../closure/work-budget/evidence/verify-20261005T103541Z-0cba9231/report.json)
is VERIFIED for seven claims through 14 mapped theorems, two identical offline
builds and six fresh source-bound reviews. Six Java semantic mutations compile
and fail refinement; invalid-proof and added-axiom controls are rejected.

For upgrades, preserve the private database and per-deployment key/password
configuration. Follow the [IIS upgrade instructions](../../deploy/iis/README.md)
to update task settings and administrator network admission deliberately. The
source release contains no private IIS ZIP or deployment credential. The user's
production IIS/Cloudflare host is not changed by this release process.

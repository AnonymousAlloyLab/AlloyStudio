# TRF-00: finite service profile and successful startup

This is the specification for the remaining TRF-00 configuration and initialization surface. The original [TRF-00 statement and pass condition](../closure/traffic-obligations.json) are unchanged. The normative candidate is [service-profile.json](../closure/traffic-refinement/service-profile.json). Writing this specification does not discharge the obligation: its source mappings, independent observation contract, dependency inventory, proofs, witnesses and frozen verifier report must all pass first.

The selected validation profile is one fresh Linux backend process listening on `127.0.0.1:8080`, persistent engines, two feedback workers, one behavior worker, a separate administrator process reservation, a 12-second feedback deadline and a 30-second behavior deadline. The optional control listener remains disabled (`control-port=0`), matching the existing default. Its positive reserved profile is still specified; enabling it requires a distinct literal-loopback port and its own admission bucket. External Luna calls are disabled during verification. This says nothing about an operator's actual configuration on another machine.

The profile records 213 finite numeric entries: the 23 HTTP fields already covered by TCFG02, existing worker/scheduler/cache/evidence/Luna/admin/store/behavior/browser settings, deliberate zero-capacity features, and explicit deployment targets. Entries distinguish source-configured values from deployment requirements that are specified but trusted. Exact units and encodings matter: MiB means 1,048,576 bytes, HTTP tokens use integer nanocredits, scalar durations use their exact integer ratios, and Boolean/subclass values do not qualify as count/duration configuration. Worker ticket integers, protocol length prefixes and browser revisions have separate encodings.

## What the profile fixes

This uses the implemented defaults, not the earlier illustrative capacity table. Production currently allows 32 scheduler jobs and 64 subscribers globally, 512 channels and 32 channels per direct peer, two Luna leaders and 32 followers. The earlier candidate's per-lane queues and 64-channel example are not silently presented as current behavior. Result and evidence caches retain their actual independent entry/byte/TTL limits. Prepared-reference caching is disabled, so its zero entry/byte budgets mean “feature absent,” not a missing positive limit.

The application semantics are explicit inputs too: Canonical is the default; AST remains available; comparison scans the complete ordered correct pool including every oracle; first-minimum ties are preserved; the learner's raw text is unchanged. Behavior uses the primary oracle, model facts, SAT4J, scope/bitwidth/sequence bound 3, sample pools of 100, four fixed categories and up to three examples in each. Existing score rounding and public disclosure policy are unchanged. Luna's role remains per-operation and per-instance guidance plus a summary. SQL parsing and bound-value execution are not modified by this profile.

The instance's exact configuration, Java/dependency/source identities and immutable catalogue input are fixed before startup. `engine_mode` is an explicit enumeration. Random generation values, administrator CSRF secret bytes, the resolved root/Java path, initial clock reading and successful OS allocation outcomes are explicit external inputs. Secret values must never appear in the manifest, reports or reviewer notes; their type/length abstraction is sufficient for this initial-state claim. Credential contents are not needed to establish empty startup state.

## Initial state and uniqueness

The initialization cut is **successful return from `Portal.__init__`, before prewarming, serving or any admitted request**. It is not a claim that the service has zero operating-system resources: three started scheduler threads and a bound listening socket already exist. Their existence/count is retained in the abstraction; native thread IDs, file descriptors, lock identities and allocator addresses are erased. A returned `Thread.start()` does not prove that the worker is already parked. Empty-queue bootstrap and condition-wait steps can transiently hold the scheduler lock, so lock ownership and idle thread program counters are also erased under the declared threading interpretation. These steps stutter in the empty ownership projection until an external request arrives. Given fixed configuration and explicit external inputs, the abstract state must be unique.

At this cut the process reservation owner map is empty, its high-water count is zero and the next serial is one. The selected root's one-shot admission is open with zero active operations. The scheduler's jobs, channels and lane queues are empty; subscribers, retained input bytes, sequence and diagnostic counters are zero. Feedback and behavior caches, evidence pins and public views are empty. The worker pool has no workers, no busy/starting/unreaped records, no launch history and no launches. Prewarming belongs to a later transition obligation.

The explainer has two available leader slots, no followers/pending work and an empty cache. Administrator authentication starts with no sessions/preauth/failures or loaded configuration; its single KDF slot is free. Administrator upload service has no drafts, a free single operation slot, and a set idle event. The HTTP public lane starts with 30 available handler positions, 60 tokens expressed as 60,000,000,000 nanocredits, a supplied initial clock reading, no owners or peers, and zero counters. Public views begin with no generation or bytes. These ownership states must be mapped to actual constructor assignments; a theorem about an independently invented all-zero record is insufficient.

A fresh process is part of this finite initialization boundary. Constructing a second Portal in a process that already owns worker reservations does not satisfy it. Likewise, startup after mutable global state has been reused is not assumed to restore global serials or ownership. Successful allocation is an explicit host interpretation. Constructor exception cleanup, failed allocation, post-startup admission histories and prewarm/shutdown refinement remain separate obligations; this block cannot claim them from a successful-return theorem.

## Memory, storage and deployment targets

The profile freezes a **4 GiB aggregate service-tree RSS target**, a 1 GiB individual backend target, a 1 GiB target for each JVM, and a 512 MiB target for the administrator provider child. The aggregate is authoritative: individual maxima are not added up and advertised as an allowed simultaneous peak. It separately specifies 512 MiB per owned worker scratch directory and 2 GiB aggregate owned scratch, plus finite encoded-snapshot byte/count targets. These are declared deployment requirements; the current Python/JVM code does not install OS containment or prove these bounds. Runtime enforcement and platform evidence remain TRF-03/TRF-21 work.

The distinction is necessary. `-Xmx256m` bounds JVM heap, not whole-process RSS; persistent JVMs separately use `MaxDirectMemorySize=64m`. The worker's 64 MiB per-job parser-source write cap does not bound every scratch file created by arbitrary JVM libraries. A 128 MiB SQLite file cap does not bound Python object expansion. Encoded cache budgets do not establish heap-size bounds. None of these facts can be promoted to a total memory proof by renaming their counters.

Direct-loopback validation has no reverse proxy or TLS termination queue; its upstream budgets are explicitly zero because that component is absent. IIS/Cloudflare relationships are declared separately: IIS backend loopback port 8080, effective feedback capacity two even though the PowerShell default requests four, one named site's scope, private control ingress, no forwarding-header quota authority, API/admin cache bypass, and explicitly specified proxy targets. The profile does not assert that a real IIS/CDN deployment has installed those settings, nor bound unrelated websites sharing the Windows host. Native macOS/Windows and actual IIS/CDN acceptance remain TRF-21.

## Required mechanical evidence

The eventual gate must reject missing, duplicated, unknown, nonfinite or incorrectly encoded profile fields; violated arithmetic relationships; incomplete observation schemas; stale manifests; and unclassified trust. It must bind the original baseline identity and complete runtime/dependency source inventory. The JSON records exact Python qualified-AST anchors as identity checks; **AST identity alone is not a semantic refinement proof**. Field extraction and each constructor's relation to the independent initial-state definition require their own registered correspondence check.

The state proof must have no admitted theorem or introduced/transitive axiom. Two isolated offline builds must agree on proof inventory, source mappings and reproducible artifacts. Finite constructor witnesses must execute the actual production constructors using controlled explicit inputs and enumerate every abstract field. Runtime checks cannot silently replace the Lean theorem, nor can a Lean model replace production correspondence. Any counterexample must retain its concrete input, observed state and failed postcondition before repair.

TRF-00 may close only when exactly one profile, source/dependency manifest, independent observation schema, TCB and verifier inventory are frozen with no required field unresolved. Its closure would establish configuration and initial-state adequacy under that declared trust. It would not close the remaining traffic transition, preservation, resource enforcement or deployment obligations.

# Side-panel tutoring chat contract

Specification recorded before the chat service implementation (2026-10-27).

The learner opens or folds a tutoring panel without leaving the exercise. Model
choices come from private deployment configuration; no credential or provider URL
is accepted from the browser. See [provider configuration](ai-providers.md).
The panel offers at most three suggested questions, generated by the cheapest
model in the selected provider's supported stack. Switching provider is explicit.

## Context and disclosure

`GET /api/chat/models` returns only model IDs, labels, providers and supported
reasoning settings. `POST /api/chat` accepts the current exercise ID, body,
revision, metric, issued channel, prerequisite tokens, optional evidence pins,
selected model/effort, a message and an optional opaque conversation token.
An explicit follow-up to a selected archived conversation may also supply
`resumeConversation: true`, only with that token and only on `/api/chat`.
`POST /api/chat/suggestions` accepts the same fields except the message.
Unknown fields, browser histories, arbitrary models, URLs and keys are rejected.
The existing same-origin, request-byte and HTTP admission boundaries apply.

The server reads the public question and learner body. If provided, hints and
behavior pins must match the exact exercise, body, channel, catalogue generation
and dependency context. Expired or mismatched pins fail without an AI call.
The existing education projection supplies the nearest-distance trace, CRUD DSL,
learner structural graph and up to twelve displayed bounded instances. Neither
the hidden oracle bodies nor the correct pool is passed to the chat service.
With no pins, chat is available for an incomplete draft but explicitly has no
compiled evidence. Chat never starts a JVM or regenerates evidence.

The prompt asks for short novice-friendly guidance tied to the question, a single
next step, and honest interpretation of bounded counterexamples. It forbids a
complete answer, fabricated evidence and treating a bounded check as proof.
Distance zero invites alternative approaches rather than inventing a defect.
Prompts and bounded plain-text output validation are defense in depth; they do
not establish a theorem about an external model's semantic behavior.

## History, cost and lifecycle

History lives only in bounded backend memory. Opaque, random history tokens bind
to a channel, exercise version, catalogue generation and dependency context;
another exercise or channel cannot retrieve or use them. Tokens survive learner
edits and metric switches within that exercise. Each exchange records its draft
revision. Every new request retrieves evidence for the current body and metric;
old transcript observations never substitute for current evidence. Tokens expire
after thirty minutes.
Keep the last six exchanges and at most 128 snapshots / 4 MiB. No browser-supplied
assistant or system messages are accepted. History truncation is disclosed.

Messages are at most 2 KiB; replies at most 4,000 characters; each recommendation
at most 160 characters. At most three distinct recommendations survive output
validation. Provider responses are bounded to 1 MiB, complete and schema-checked.
The provider request disables storage where supported. Errors contain no raw
provider body, credentials, or private configuration.

Chat and suggestions share the explanation service's two-call semaphore. Only
one call per learner channel may run at once, with no waiting work queue. A
bounded two-minute cache reuses identical requests, scoped to provider/account,
public context and history. Superseded contexts are checked before dispatch and
before publishing or storing results. Cancellation cannot revoke an already
sent provider request; its slot stays occupied until it finishes.

Opening the panel, an explicit refresh, or a completed conversation turn may
request recommendations. Typing, fetching catalogue entries and rendering the
panel never initiate model calls. Edits, exercise/metric changes and folding
abort browser requests and suppress stale UI updates. Editing retains the local
conversation and marks earlier replies as belonging to an older draft. Switching
model, provider or reasoning effort also preserves the conversation and unsent
message. The next explicit send passes the retained discussion and current
learner context to the selected configured provider. Assistant messages identify
the model and effort that produced them. Switching makes no provider call and
clears suggestions from the previous selection; an already dispatched suggestion
is allowed to finish, with its stale output discarded before another send.
Selectors wait for an active chat reply to finish. Changing exercise, editing
session or prerequisite context, or selecting New chat, clears the conversation.
Public assets and private modules must be included in the Unix,
Windows and IIS packaging inventories.

The composer remains editable while a reply is pending. If a reply fails or
cannot be matched to the draft, preserve any newly typed text exactly (including
whitespace); restore the unanswered question only if the composer is empty.
Channel expiration discards expired history and evidence, but keeps that question
visible for manual recovery. Recovery never retries or submits a queued message
automatically.

Model and reasoning controls live inside the message input frame, with visible
labels and native keyboard-accessible menus. On desktop, opening the tutor keeps
the editor and repair-trace column side by side. Smaller non-modal layouts reserve
space for the tutor and stack the workspace so feedback remains reachable without
closing chat. Phones retain the existing modal panel and focus handling.

Explicit model/effort choices may be remembered in browser storage, then validated
against the next configured catalogue. Credentials, conversation tokens and chat
text are never stored with this preference. Storage failure leaves selection
usable for the current page. Short reasoning guidance describes possible extra
latency without promising model quality or an exact price.

Immediate learning starters share the three-question slot with generated
suggestions. They fill an empty composer, never overwrite an existing draft, and
never submit or generate provider work themselves. Selecting a generated
suggestion retains any separate unsent question. New chat also preserves that
question while resetting the active backend history capability.

New chat saves a local transcript for the History view: at most five archived
conversations and 64 KiB of UTF-8 message text, with oldest content evicted first.
The archive stays in tab memory for this exercise/version/prerequisite context;
reload or a context change clears it. It is excluded from progress exports.
Reading, selecting or copying text and selecting Continue this chat make no
provider request. Reusing an archived user question only fills an empty composer.

Only an explicit subsequent Send may attach the selected archive's opaque token
with `resumeConversation: true`. The backend checks ownership and expiry as usual,
then produces bounded, role- and revision-preserving excerpts of its own retained
history before the provider call. It labels the excerpts incomplete and keeps the
fresh learner context authoritative. Compression is deterministic and makes no
additional model call; it is not an AI-generated semantic summary. It does not
overwrite the stored original turns. The resumed token's descendants retain this
abridged mode for later replies and recommendations, so follow-up work cannot
silently resend the full older discussion. Suggestions cannot initiate resume mode.
An expired token cannot be reconstructed from browser transcript text. The local
transcript remains readable; the learner can start a fresh discussion instead.

## Acceptance checks

- Model/effort and credential isolation, malformed configuration, disabled mode.
- Learner-only context with CRUD and exact bounded examples; no engine calls.
- Forged, cross-channel, expired and superseded evidence/history rejected.
- Safe structured output, maximum recommendations, response-size and error bounds.
- Shared concurrency, per-channel exclusion, caching, expiry and history limits.
- Fold/open, keyboard access, model changes, responsive layout, stale results and
  literal text rendering in browser regressions.
- IIS asset/runtime inventories and packaged copy checks.

These are executable regression obligations, not a renewal of older frozen Lean
or mechanical-closure certificates over different source hashes.

## Implementation verification

The model, service and HTTP regression suites cover
the current question and learner tree, all twelve bounded instances, withheld
target expressions, history ownership, continuity across edits, exact fresh pins,
stale replies, provider schemas, cache/account isolation and concurrency limits.
The browser regressions also cover retained conversations across edits, metric
changes and checks; earlier-draft labels; channel renewal; UTF-8 message limits;
and waiting for suggested questions before sending a message on the same channel.

A live GPT-6 Luna check on `graphs-inv1` continued one conversation after replacing
the learner draft: the new turn used revision 2 and the new distance (3 rather
than 8). The reply discussed the revised expression and explicitly acknowledged
that behavioral evidence was absent for that new request. Live suggested prompts
and a rendered chat reply were also checked in the portal. Claude and Gemini
adapters were tested with synthetic provider responses, not live credentials.
IIS inventory/package tests include both private Python modules, the public JS
module, hashed asset imports and missing-file rejection.

## Ingress registration

The named `RouteServices` capability bundle now adds only `chat: object`, bound
by its builder to `app.chat`. The two corresponding AST fingerprints in
`closure/patch-contracts/ingress-boundary.json` were reviewed and updated for
this addition. Removing that field and keyword exactly reproduces the previous
registered fingerprints. Every registered Handler fingerprint is unchanged;
existing ingress-method and DeadlineReader comparisons still use their frozen
templates. A negative regression substitutes the whole application or its socket
for the chat capability and requires rejection. This records reviewed structural
drift only: no historical evidence or Lean production-closure claim is renewed.
